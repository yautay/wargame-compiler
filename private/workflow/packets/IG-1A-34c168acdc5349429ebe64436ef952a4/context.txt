# Wargame Compiler

WGC turns a WGU knowledge base and complete source materials into an evidence-backed
Instruction Graph, formal rule semantics, a compiled rules package, and deterministic
legal actions and state transitions. A future AI opponent spends its context on
strategy and chooses through a compact player interface. Gameplay legality never
requires an LLM call.

The product target includes the **entire SPQR 5E core rulebook from the start**.
Incremental tasks build lasting parts of that product. No further POC is planned.
There is currently no new importer, compiler, game runtime, or AI opponent.

Start with [status](docs/STATUS.md), [handoff](docs/HANDOFF.md), and the
[workflow](docs/work/WORKFLOW.md). The only task/status source of truth is
[queue.json](docs/work/queue.json); [roadmap](docs/ROADMAP.md) and task cards are generated.

- [Architecture](docs/IG-WGU-ARCHITECTURE.md), [data contracts](docs/IG-DATA-MODEL.md),
  [mechanics and profiles](docs/IG-MECHANICS-PROFILES.md), [legal action contract](docs/IG-LEGAL-ACTIONS.md).
- [Implementation plan](docs/IG-PLAN.md), [operator prompts](docs/work/PROMPTS.md),
  [local skills](docs/work/SKILLS.md), [environment evidence](docs/work/ENVIRONMENT.md).
- [Archive locations and explicit access](docs/ARCHIVES.md).

Repository prose and tooling use English. Publisher text, imported KB data, and
immutable historical records retain their original language and bytes. Game content,
source documents, positions, and source-derived examples belong in `private/`.

```powershell
pwsh -NoProfile -File scripts/check.ps1
.\.venv\Scripts\python.exe scripts/workflow.py next
.\.venv\Scripts\python.exe scripts/workflow.py packet --task IG-1A
```

The packet command prepares local context; it does not start a model or change task
state. Checks validate planning and workflow, not the unimplemented game's correctness.
Archive integrity is an explicit separate command, never part of routine checks.

# Local task workflow

The only authoritative queue, dependencies, task content and status are in
[queue.json](queue.json). Cards, [roadmap](../ROADMAP.md) and the generated portions
of status/handoff are projections checked by `scripts/workflow.py validate`.
Edit queue.json, run `scripts/workflow.py render`, then `scripts/check.ps1`.
This tool is a local planner; it launches no model, chat, agent, scheduler or API.

## Roles and ownership

The coordinator selects ready work, refines future contracts, owns the queue, checks
handoffs and records acceptance evidence. The executor owns only the task's listed
write paths. The independent reviewer reads the frozen result and writes review findings;
they do not silently repair the executor's code. Source-meaning review is separately
identified. The owner (or explicitly authorized human) accepts exact semantic revisions.
Model review and green tests never substitute for that decision.

Default execution is sequential: one claimed task and one writer. A separate review
session may use the same requested Sol/high configuration but a fresh reviewer identity
and task context. No sessions are created automatically. Parallel work needs explicit
operator authorization, satisfied dependencies, disjoint writes, and a coordinator-owned
integration task. Two tasks writing queue.json are never parallel writers.

## State machine

| From | Allowed next states | Gate |
|---|---|---|
| planned | ready, blocked | Dependencies done; context available; refinement resolved |
| ready | in_progress, blocked | Executor identity, actual config evidence, exact scope and checkpoint |
| in_progress | review, blocked | Frozen delivery manifest, meaningful checks and handoff |
| review | changes_requested, accepted, blocked | Separate technical review; meaning review and human decision when required |
| changes_requested | in_progress, blocked | Bounded repair scope and new attempt |
| accepted | done, changes_requested | Coordinator verifies every criterion, evidence and required owner decisions |
| blocked | planned | New evidence resolves recorded blocker; reevaluate readiness, never jump to done |
| done | planned | Explicit reopening reason; prior acceptance preserved in event history |

`ready` is explicit and checked, not inferred from file existence. `next` prints the first
ready task in queue order. At most one task is in_progress/review/changes_requested/accepted.
`done` means its lasting deliverables, tests, independent review and applicable human
acceptance are complete. `blocked` records missing fact, failed assumption or unavailable
input, impact, smallest resolution action, and owner. Source gaps can be valid importer
outputs while still blocking later gameplay; do not mark import blocked for every missing PDF.

Use `transition --task ID --to STATE --evidence PATH`. Evidence is JSON with `role`,
`actor`, `summary`, `criteria`, `artifacts`, `model`, `reasoning`, `configuration_evidence`,
and optional `semantic_decision`. Unknown measured configuration is null with a reason.
For delivery/review/acceptance also supply `checks`, a nonempty list of command and
exit_code records. All required checks must have exit code zero. In-progress claims
require confirmed `model: gpt-6.1-sol` and `reasoning: high`; unknown configuration
is recorded as a blocker until the operator confirms the actual session settings.
The command checks structural gates and file hashes, not the truth or authority of a
human statement. Evidence is append-only by hash in queue events; changes invalidate checks.
See [evidence shapes](EVIDENCE.md) for a checkpoint/delivery example. Executor status
updates go through the transition command; the coordinator owns structural queue edits.
For a semantic task, accepted requires a human decision artifact from the owner or a
documented authorized reviewer. Do not fabricate one. Routine technical acceptance can
be recorded by the coordinator after independent review without another owner confirmation.

## One task cycle

1. Coordinator validates queue and chooses `next`. Resolve `refine` before readiness.
2. Generate a packet with exact allowed context. Binary source references are hashed,
   not dumped into text; read only pages/IDs named by the task. External WGU context is
   explicitly scoped in the card, never scanned through historical manifests.
3. Operator starts the selected executor manually using [the launch prompt](PROMPTS.md).
   Confirm Sol/high from UI/session metadata; requested settings are not evidence.
4. Record claim and checkpoint; implement only this increment; record changed files,
   checks, measured usage and unresolved assumptions. Preserve unrelated working changes.
5. Freeze delivery hashes and enter review. Operator supplies the review prompt to a
   separate reviewer. Evaluate source meaning separately from code mechanics.
6. Repair scoped findings, rerun affected checks and obtain a new review of changed hashes.
7. Coordinator records acceptance then done, renders views, makes the next eligible task
   ready, and prepares a new handoff. Do not start the next task just to finish this one.

## Refinement and corpus partitioning

`refine` tasks are not executable until exact prerequisites/paths/cases are pinned. Edit
the record to `implementation` or `content` after refinement; keep the decision in events.
For a corpus task, create bounded child records with explicit target IDs, context-only
IDs, source hashes/pages and disjoint output paths. The parent becomes a closure task
depending on children, while children inherit the parent's former dependencies (never
depend on the parent). Rewire downstream tasks through parent closure. Validate the DAG,
check target-set coverage without overlaps, and render child cards. No recursive platform
or agent manager is needed. Work partitions do not reduce the full-rulebook target.

## Checkpoints, interruption and conflicts

Write `private/workflow/runs/<task>/<attempt>/checkpoint.json` before starting and after
each usable increment: task/attempt, actor, actual config, base file hashes, changed-file
hashes, input packet hash, completed criteria, command results, blocker and next operation.
Freeze a delivery manifest of all reviewed files and record reports in the same run folder.
Do not overwrite prior attempts. A interrupted task remains in_progress until triaged.
Resume by comparing checkpoint hashes with disk and the current queue; record divergences,
retain both versions and resolve only owned files. Never reset, clean or stash the worktree.
If an unexpected writer changed an owned path, block that path and ask the coordinator
to integrate. A checkpoint is not a commit and never authorizes push.

At most two repair cycles per review finding and two retries for the same unchanged
failure. Then block with evidence and the smallest decision needed. A new hypothesis
or changed external condition must be recorded before another attempt. No silent scope
expansion or weakened tests to clear a blocker.

## Measurements and report

Record start/end UTC, elapsed wall time, executor/reviewer identities, requested and
observed configuration, token counts only if exposed, operator time only if reported,
tests and defect counts by severity. Unknown values are null, not zero. Separate code
quality from source meaning and full-profile readiness. No invented monetary cost.
Final handoff includes outcome, paths/hashes, criteria met/unmet, commands and exits,
independent review, human decisions where needed, remaining risks, and next exact action.

## Permissions and context limitations

Packets enforce their own allowlist and reject history paths, path escapes and symlinks.
They are not an OS sandbox for arbitrary tools. `.rgignore` controls default ripgrep only;
explicit paths, `--no-ignore`, other tools and Git can bypass search exclusions.
Read [archive isolation](../ARCHIVES.md) before any historical access. The current session
cannot migrate outside its writable roots or install under protected `.agents/`.

# WGC architecture

This is the active architectural proposal; machine contracts are established task by
task. [Queue](work/queue.json) defines execution order, [data model](IG-DATA-MODEL.md)
defines record invariants, and [runtime contract](IG-LEGAL-ACTIONS.md) defines gameplay.

```mermaid
flowchart LR
  KB[WGU KB] --> IN[Frozen inputs and read-only adapter]
  SRC[Complete rulebook and required materials] --> INV[Independent source inventory]
  IN --> IG[Source IG with evidence and gaps]
  INV --> IG
  IG --> SEM[Typed rule semantics]
  SEM --> REV[Source review and human acceptance]
  REV --> REF[Reference executor]
  REV --> COMP[Compiler]
  COMP --> PKG[Immutable rules package]
  PKG --> RUN[Deterministic legal runtime]
  REF --> EQ[Differential checks]
  RUN --> EQ
  RUN --> VIEW[Player view and exact choices]
  VIEW --> AI[Strategy selection]
  AI --> VAL[Validate against current revision]
  VAL --> RUN
```

## Ownership and boundaries

WGU maintains its KB. WGC reads a frozen directory snapshot and original documents,
preserves both, records discrepancies, and builds versioned interpretations.
It never edits WGU as an import side effect. Corrections are separate WGC proposals.
The runtime owns authoritative game state and history; an LLM description is not state.
AI owns strategy only. UI, online services, providers, and a graph database are not
prerequisites. Start with local JSON/JSONL, deterministic exports and derived indexes.

| Module / future path | Responsibility | Output |
|---|---|---|
| `src/wgc/inputs/` | Snapshot, safe paths, hashes, availability | Immutable input manifest |
| `src/wgc/wgu_adapter/` | Safe parsing, unknown fields, identities | Import records and origin bindings |
| `src/wgc/sources/` | Pages, regions, evidence, independent inventory | Coverage denominator |
| `src/wgc/reconcile/` | Matches, disagreements, omissions, editions | Source IG and explicit gaps |
| `src/wgc/review/` | Review packets, decisions, freshness | Revision-scoped decision ledger |
| `src/wgc/semantics/` | Types, expressions, actions, procedure IR | Formal IG linked to source clauses |
| `src/wgc/reference/` | Simple deterministic execution | Independent comparison baseline |
| `src/wgc/compiler/` | Type/closure checks and lowering | Reproducible executable package |
| `src/wgc/runtime/` | Actions, validation, events, replay | State transitions and legal choices |
| `src/wgc/player/` | Visibility, compact views and deltas | Player-safe decision interface |

These are planned boundaries, not existing implementations. Tests live in corresponding
`tests/<module>/` directories; public fixtures are synthetic. Source-derived data lives
in `private/ig/projects/spqr/`. Planning tools in `scripts/` do not implement these modules.

## Import contract

Primary input: game `wgu.yaml`, complete `kb/`, and explicitly enumerated auxiliary
files. The optional `wgu/kb-bundle@1` route is later work: the current exporter omits
some auxiliary files and full source configuration, abbreviates revision information,
and adds a generation time. A bundle alone cannot establish complete input accounting.

Freeze raw bytes, relative paths, sizes, SHA-256, schema/adapter versions and import
configuration. Git commit and dirty state are supporting metadata; record unknown
when inaccessible. Detect source changes during snapshotting. Reject unsafe YAML tags,
duplicate keys, traversal, and paths escaping the allowlist; preserve unknown fields.
Unavailable PDFs block source verification, not import of available KB records.

| WGU entity | Source IG mapping | Never infer |
|---|---|---|
| Rule, when/effect/exceptions | Clause container, addressable aspects and groups | Executable logic or correct atomization |
| Source locator | Provenance claim, then evidenced region binding | PDF page identity or exact quotation |
| refs / see | Navigational references | Required semantic dependencies |
| Relations | Typed candidates, original status retained | IG acceptance from `verified` |
| Procedures | Nested steps, local identities and declared order | Binding lifetime, triggers or continuation semantics |
| Tables | Axes/cells/notes; distinguish editorial summaries | Literal publisher table from `complete: true` |
| Terms without IDs | Persistent mapping registry | Identity from list position or content hash |
| Ambiguities / changes | Claims, gaps and evidence | Human resolution or complete edition history |
| scenarios / questions | Imported evaluation candidates | Battle scenarios or independent expected answers |
| Unknown fields and files | Lossless payload plus mapping status | Silent exclusion |

One KB rule may map to several clauses and vice versa. IDs are stable and separate
from content revisions. Reordering, splits, merges and ambiguous matches preserve
lineage and require explicit resolution. Wildcards and subpoint references retain
their raw form until an exact target set is justified.

## Complete sources and reconciliation

Inventory all 44 PDF pages independently of the KB: headings, clauses, notes, examples,
tables, legends, diagrams, and editorial regions. Keep PDF page number separate from
printed labels. Text extraction is a helper; diagrams and meaningful decorations need
image evidence. Every region is represented, partially represented, a gap, or excluded
with a reason. Gaps never count as represented content.

Reconcile all imported records: exact/partial match, contradiction, missing KB content,
missing source, or possible duplicate. Preserve KB bytes, candidate interpretations,
evidence, and corrections separately. Cross-chapter exceptions and external tables
remain explicit dependencies. A table assembled by KB authors can cite multiple clauses;
do not invent a single publisher region for it.

Each profile pins edition, mode, options, scenario, source revisions and compatibility
decisions. A 2018 4E scenario book does not inherit 5E authority from the KB manifest.
Do not invent universal 'newer wins' or 'more specific wins' precedence. Unofficial
aids remain secondary material. An empty errata list is not proof that no errata exist.

## Revision, review and updates

One logical source IG links to one formal semantic representation; the executable
package is derived and immutable. All operations map back to exact clause/evidence
revisions. Do not maintain three independent hand-edited descriptions of a rule.

Review records pin target revision/aspect, evidence, profile and dependencies.
Technical checks, source/meaning review, and human acceptance are separate. Model
observations cannot grant semantic acceptance. Incomplete review bases imply unknown
freshness; changed bases imply stale. Acceptance is never inherited by a changed aspect.

Updates compare old WGU, new WGU and current WGC. Deletion in WGU retires provenance,
not IG history. Recompute impact through reads/writes, triggers, bindings, table/profile
dependencies and unresolved references. Preserve decisions; request new ones for affected
meaning. Rebuild packages and replay regressions before promoting an updated profile.

## Product readiness

Report input accounting, source coverage at each representation level, current human
acceptance, resolved dependencies, compiled scope, and gameplay readiness separately.
Opaque text is valid in a working source IG. If it affects legal choices, timing,
visibility, costs or effects, it blocks executable readiness of the dependent scope.
Unknown conditions cannot be assumed inactive to bypass a dependency.

# IG data contract proposal

This document consolidates the earlier `ig-draft-0.2` design. It is not a machine schema
or accepted game semantics. IG-1A establishes the source contract; IG-3A establishes
the executable language after source reconciliation. See [architecture](IG-WGU-ARCHITECTURE.md).

## Identity and record envelope

Each record has stable `id`, `record_type`, `schema_version`, `revision_id`, `run_id`,
`supersedes_refs`, and canonical content hash. Stable identity is separate from revision,
file path, array position and content hash. External WGU IDs are namespaced by KB.
`origin_bindings` link many-to-many IG IDs to input snapshot/file/field locators.
Anonymous terms and relations use a persisted identity registry; ambiguous rematches
become conflicts. Split/merge lineage does not transfer acceptance automatically.

References used as active rules resolve only in the selected snapshot. Historical
review and supersession references resolve in an immutable revision store. A snapshot
selects at most one revision per ID, but may retain conflicting assertions with different
IDs. The presence of an old revision does not activate it. Namespaced IDs must be safely
encoded as Windows file names rather than used literally with colons.

## Collections and invariants

| Collection | Minimum content and constraints |
|---|---|
| sources / artifacts | Role, publisher/system/edition/language, part, media type, bytes, SHA-256, availability and compatibility |
| regions / evidence | Source revision, PDF page (1-based), printed label, reading order, coordinate/offset convention, precise region links |
| nodes | Sections, clauses, concepts, procedures/steps, tables/axes/cells, diagrams, components and mechanical definitions |
| assertions | Subject, stable aspect, knowledge state, literal/normalized/interpreted representation, value, scope, evidence and gaps |
| semantic_groups | Stable aspect IDs and explicit condition/effect/exception/timing composition |
| relations | Typed directed link, applicability, target status, candidates, evidence, requirement grouping |
| gaps | Missing source, unreadable, unprocessed, ambiguity, conflict or unsupported interpretation; affected targets and blocked operations |
| profiles | System, edition, rules mode, options, scenario, maps/counters, pinned materials and compatibility decisions |
| reviews | Exact targets and basis revisions, kind, actor role, decision/observation, scope and supersession |
| coverage | Inventory revision, region, representation level, status and exclusion reason |
| snapshots | Selected revisions and hashes, profile, conflicts, manifest and independent readiness reports |
| runs / evaluation | Raw proposals, context manifest, actual configuration evidence, measurements and independently justified expectations |

`sources.role`: rulebook, errata, faq, scenario, map, counter_sheet, player_aid, other.
Edition labels do not establish compatibility. Exact transcription, normalization,
uncertain symbols and interpretation remain distinguishable. Evidence roles are direct,
context and counterevidence. Attaching a whole page does not prove every assertion.

Nodes include action, event_type, state_variable, resource, timing_window, choice,
selector, spatial_policy, randomizer, calculation and outcome. Their source representation
may precede formal execution. A generic payload field alone is not demonstrated support.
Editorial parentage is not an execution dependency. Clause boundaries preserve complete
conditions and effects; aspects can be separately reviewed inside a container revision.

## Knowledge and representation

Knowledge states: `known` (evidenced proposal, review separate), `established_absent`
(source proves absence in an explicit scope), `unknown` (null plus gap/reason), and
`not_applicable` (null plus reason). Missing fields and empty lists never prove absence.
Representations: literal, normalized, interpreted. A normative assertion has an explicit
execution impact: formal, informational with reviewed rationale, or blocking.

Facets include transcription, condition, effect, parameter, exception, timing, scope,
definition, permission, obligation, prohibition, trigger, cost, choice, calculation,
transition, duration, aggregation, visibility and victory. A shared subject ID does
not bind several conditions to the right effects; semantic groups do that explicitly.
Units, comparison operators, rounding stage, temporal bounds and causal filters are typed.
Opaque is preserved text with an execution limitation, never a runtime LLM callback.

## Relations

Navigation (`mention`) is distinct from dependency (`procedure_use`, `table_use`,
`definition`, `condition`). Exception/modification points from modifying rule to base.
`applies_to` points from clause to scope object; `illustrates` from example to rule;
`precedes` from earlier to later step with its condition. `continuation` alone is not
an executable stack frame. Mechanical relations are specified in the mechanics contract.

`target_status`: resolved, unresolved, ambiguous, unsupported. Non-resolved references
retain raw locator, edition, candidate IDs and a gap. Targets can select exact aspects.
`requirement`: required, conditional, informational; groups explicitly specify all/any.
Unknown applicability cannot be treated as false. Rule graphs may contain cycles;
the task dependency graph may not. Procedure cycles need termination/continuation rules.

## Reviews and readiness

Review kinds distinguish transcription, interpretation, source composition and situation
outcomes. Roles distinguish human_owner, authorized human_reviewer, model, validator.
Only an authorized human grants semantic acceptance. Store the decision artifact,
actor, exact target/aspect revisions, scope and basis (sources, definitions, bindings,
profile and dependencies). Basis completeness is complete, partial or unknown.
Freshness is independently computed as current, stale or unknown. A newer date does
not resolve contradictory decisions; explicit supersession and rationale are required.

Coverage statuses are represented, partial, unprocessed, excluded, measured separately
for transcription, descriptive semantics and formal semantics. Exclusions need a reason
and approved scope boundary. Do not add overlapping context regions to the denominator.
Executable readiness is a query over snapshot/profile/dependency closure and available
state/history, not a global `rule_ready` flag.

## Storage and validation

Use `private/ig/projects/spqr/{inputs,sources,records,runs,reviews,snapshots,reports,evaluation}/`.
The promoted source registry at `private/ig/sources/` is a read-only input to later project
snapshots. Source-derived material stays private; public schema fixtures are synthetic.
One record per file is optional. Containers retain stable aspect IDs and raw input mapping.
Indexes are derived. Snapshot states draft/sealed describe structural integrity, not quality.

Validate identity/revision uniqueness, hashes, typed references, evidence scope, unknown
values with gaps, table notes/axes, group composition, review authority and freshness,
coverage denominators, conflicts, and historical versus active reference resolution.
The first schema must represent all required mechanical concepts without implementing
a universal game language. Later formal contracts must make those concepts executable.

Tests need a clause spanning pages, cross-chapter exception, table note, missing unit,
procedure cycle, edition conflict, partial acceptance and regression after dependency
change. Expected meanings are justified against sources, independently of implementation.

# Mechanical semantics and profiles

The shared IG represents mechanical concepts; each profile supplies the actual rules.
SPQR is first. OSG and GCACW remain future independent profile work, not prerequisites
or evidence that SPQR semantics generalize. Bibliographic and research history is outside
default context. This consolidation preserves its useful design constraints below.

## State, history and causes

State variables specify type, units, owner, bounds and reset rules. Boolean, enum,
integer, rational, set, reference and multiset/physical-instance pools are distinct.
Organization, activation, fatigue, losses, ammunition and command status can coexist;
do not collapse them into a universal status enum.

Events record cause, attempt/commit/invalidation state, read moment, ordered writes,
limits and reset window. Writes include set, increment, decrement, flip, move, remove,
schedule and invoke, with explicit targets. Equal final values can have different
consequences when caused by an action cost versus combat. Preserve rule-relevant history:
prior positions, first occurrence, attempted actions, counters, used participants and
already-paid costs. Missing history is unknown, not zero. Permission, obligation and
prohibition differ; attempt and success costs may differ.

## Time, reactions and continuation

Time is a hierarchy of instances: turn, phase, segment, activation, step and event as
needed by the profile. A phase name is not an occurrence. Counters scope to object,
side, activation, turn or game. Procedures specify actor, guard, inputs/outputs,
branches, loops, completion, failure and reaction windows.

Windows specify trigger, eligible player, opening/closing conditions, attempt limit and
resume/replace/cancel/restart policy. Continuations bind a particular invocation frame,
local environment and return point. Cancellation does not imply global rollback;
specify which effects, costs and history survive. Priorities and simultaneous resolution
must come from sources, including who breaks a tie. No universal reaction queue is assumed.
Temporary effects define start, expiry, checkpoint, snapshot reads and refresh rules.

## Choices and calculations

Choice contracts specify owner, selector, cardinality, constraints, binding ID, lifetime
and reselection policy. Player choice, automatic selection and randomness are different.
Bindings belong to invocation instances. Eligible, selected, committed, participating
and affected sets can differ. A participant used across several steps cannot silently
be replaced by a more advantageous one in each calculation.

Aggregation specifies set/filter/measure/operator and modifier order. Size, combat
strength and other measures use distinct units. Loss allocation specifies deciding
player, targets, proportions, overflow and elimination timing. Calculations are ordered
add/subtract/multiply/divide/compare/round/clamp/column_shift/lookup/decode/invoke steps.
Changing input strength, a die roll, a table column or the decoded outcome are distinct.
Use rationals where needed; rounding includes stage, method and beneficiary.
Modifier stacking explicitly defines addition, exclusion, replacement, cap or choice.

Tables preserve ordered axes, inclusive/exclusive boundaries, out-of-range and missing-cell
policy, units, merged cells, note scopes, meaningful decorations and legends. Lookup pins
the table revision and participant bindings. Outcomes retain original symbols plus ordered,
conditional effects and triggered procedures. A symbol without its legend is incomplete.

## Geometry

Locations qualify map, sheet and hex label. Geometry includes occupied hexes, anchor,
orientation, relative zones and pivot policy. Track hex/edge terrain, elevation and
infrastructure state. Movement, retreat, command, supply, ZOC and LOS are distinct
spatial policies even on the same hex grid. Specify metric, endpoints, rounding,
admissible nodes/edges, cost and exceptions. Multihex units count once as entities.

Distinguish path existence, all-path conditions, optimality and player selection of tied
paths. Reachability is not shortest path or retreat priority. Stack constraints specify
order/composition/limit/checkpoint. Off-map locations are named zones with ownership,
capacity and transfer rules. Unread topology can remain a source gap but blocks execution.

## Randomness, visibility and victory

Randomizers specify physical symbols, meaning, draw count, combination, independence,
replacement and pool composition. A d10 is not automatically 1–10. Store raw/modified
result, draw identity, reroll policy and sharing across targets. Pools with duplicate
symbols require multiplicity or physical identities; set semantics lose probability.
Unknown composition means unknown distribution.

Visibility applies to the entire observable response: state, domains, rejected choices,
reason codes, proof paths, gaps, identifiers, cursor metadata and caches. A privileged
tool's full state is not player knowledge. Define legal attempts under hidden information
and when outcomes reveal facts. Never filter only the final JSON field after computing
a secret-dependent action menu.

Victory specifies metric, counted set, checkpoint, comparison, termination and tie rule.
Scenario thresholds, immediate endings and end-of-turn assessment are distinct.
Territorial control may require history as well as occupancy.

## Mechanical dependency directions

| Relation | Direction |
|---|---|
| reads / writes | Assertion or step → state/resource definition |
| triggers | Event type with cause filter → procedure/step |
| schedules | Assertion or step → future window |
| resumes | Reaction procedure → parent continuation point |
| constrains | Constraint → choice/action/path/outcome |
| uses_binding | Step/assertion → participant/value choice definition |

Change impact follows all these links as well as tables, profiles and ordinary references.
An incomplete dependency graph cannot certify absence of regressions. Each capability
needs evidenced examples; merely adding a payload field is not support. Representation,
semantic review and resolvability of a particular query remain independent assessments.

# Deterministic legal action contract

The source IG provides evidence; typed semantics describe rules; the immutable compiled
package supports fast local execution. See [architecture](IG-WGU-ARCHITECTURE.md).
This is a logical library interface, not an HTTP service or implemented runtime.

| Operation | Input | Output |
|---|---|---|
| decision_view | State, profile, viewer | Permitted observations and current decision owner/window |
| legal_actions | State, package, entitled actor | Legal actions or exact parameter domains with dependent constraints |
| validate_action | Package ID, state revision, actor, complete action parameters | legal / illegal / blocked and stable permitted reason codes |
| apply_action | Action revalidated against the same package and current revision | Atomic state/event delta up to the next decision or chance window |
| chance_options | Chance node, rule/pool state | Permitted outcomes, probabilities and requirements |
| resolve_chance | Allowed result from authoritative randomness | Deterministic continuation and recorded draw |
| explain | Validation result or event trace, viewer | Visibility-safe reason and evidence references |

Queries do not mutate state or draw randomness. The same package, state, history and
action give identical results and stable ordering. Record random outcomes for replay;
the player model does not control the random source. Validate package ID, state revision,
decision window, actor and parameters again at application. A previously offered action
ID is not lasting authorization. Stale proposals have no effects or paid costs.

Execution preserves invocation-local bindings, reaction ownership, continuation stack,
cause, timing, attempt/success costs and committed event history. Apply each cost once.
Define transaction boundaries at decisions/chance nodes and the profile's cancellation
policy. Reactions do not automatically resume a parent; cancellation is not global rollback.
Replay checks all event/state hashes with the pinned package and recorded random outcomes.

## Soundness, completeness and unknowns

Every fully specified action labelled legal must pass validation (soundness). Every
legal action in the declared scope must be represented (completeness). A strategic
shortlist is a separate AI layer and cannot redefine either property. Generator-validator
agreement alone is insufficient: they can share the same omission. Compare against
source-justified expected cases and exhaustive small-state oracles using an independently
written enumeration, then compare reference and compiled execution.

Avoid materializing a giant Cartesian product of actors, targets, paths and orderings.
Expose exact domains and constraints, bind parameters stepwise, and enumerate lazily.
Cursors pin package/state/window/viewer/query; pagination must not skip or duplicate
choices. Time limits explicitly mark incomplete output. First-page absence does not mean
illegality. Broad candidates are not legal until checked. Missing history, source rules,
profile or data yields blocked, not illegal or an empty complete menu.

Opaque or unresolved meaning affecting legal choices, timing, visibility, cost or effect
blocks executable readiness. The runtime never asks an LLM to fill that gap. A profile
release needs closed dependencies, including external tables, maps and counters.
Complete import, full source representation, semantic acceptance, successful compilation
and gameplay readiness are separate claims.

## Information boundaries and AI context

Define legal attempts under player knowledge separately from privileged outcome resolution.
Two states indistinguishable to a player must not leak forbidden information through
menus, reason codes, explanations, counts, cursors, identifiers, caches or deltas. Test
the whole response, not just visible fields. Cache keys include package, profile,
revision/dependencies, decision window and visibility context. Audit observable timing
where secret-dependent work could expose information.

AI receives compact observations, stable visible object IDs, exact choices/domains and
strategic features the player may know. It can request permitted details. Default context
excludes the full rulebook, IG, proofs and irrelevant history. Revisioned deltas must detect
gaps and trigger resynchronization. Compression must preserve player-available information
and action completeness. Failed/malformed AI selections are rejected locally with no mutation.

## Performance and regression evidence

Establish a simple reference executor before optimization. Compile type checks and static
dependencies ahead of play. Index by window, action type and object type; invalidate
caches through affected state dependencies. Compare every optimization with the reference.

Measure zero LLM calls on legal paths; p50/p95/p99 latency and memory; cold/warm/invalidated
cache; candidate/domain counts; large states, nested reactions and combinatorial paths;
player-view bytes and token estimates with named tokenizer; details requested per decision;
replay agreement, privacy and exact action coverage. Operator approves concrete thresholds
on named hardware and a fixed state corpus before performance acceptance. No latency or
token claim is accepted without measurement. Lower context cost alone does not prove
better strategy. Source changes trigger revision impact review, rebuilt packages and regressions.
